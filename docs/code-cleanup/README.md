# Чистка кода: план и отметки выполнения

## Кратко для владельца

- **Код в хорошем состоянии.** Ни одного полностью мёртвого файла кода, все скрипты и
  проверки используются. Из зависимостей лишние только две на сервере (`uuid`, `joi`).
  Предыдущие чистки поработали.
- **Важнее всего — четыре вещи. Они касаются безопасности и денег, а не красоты кода.**
  1. **Адрес посетителя.** В 11 местах сервер берёт адрес, который посетитель может
     подделать. Из-за этого обходятся ограничения на число попыток, в том числе на поиск
     анкеты по SSN. И этот же адрес записывается в юридическую отметку о согласии с
     соглашениями (Ч1.1).
  2. **Тестовые данные в боевой сборке.** Они попадают в сборку сайта для людей, а вход под
     пробной учётной записью держится на одном выключателе (Ч1.2).
  3. **Опасные инструкции в README.** README советует команды, которые выложат сайт прямо
     на Production мимо выпуска. Рядом лежит настройка, открывающая хранилище файлов всем
     сайтам (Ч1.3).
  4. **Медленная карточка кандидата.** Каждое открытие карточки читает базу около 310 раз;
     после Ч2 будет около 10. Карточка откроется быстрее, а счёт за базу станет меньше.
- **Остальное — порядок:**
  - убрать 3 ненужные функции сервера и 4 триггера на старую коллекцию;
  - убрать около 230 строк мёртвого кода и 183 лишних экспорта;
  - свести дублирующуюся логику: маскирование SSN считается в 6 местах по-разному;
  - навести порядок в документах.
- **Что меняется для пользователей.**
  - Почти ничего видимого: быстрее открывается карточка кандидата и главная страница.
  - Кнопка «Email link» перестанет появляться для адресов, которые сервер не примет.
  - Видимые изменения цветов, форматов дат и прав доступа — только после вашего решения
    (вопросы ниже).

## Как работать по плану

- **Каждая строка «Ч» — один небольшой PR.** Внутри PR действует порядок из `AGENTS.md`:
  - найти и подтвердить причину;
  - написать тест;
  - исправить;
  - прогнать проверки;
  - обновить APP_BRIEF.
- **Серверные функции удаляются только по правилам из [audit.md](./audit.md#правила-безопасности-для-любого-удаления).**
  - Сначала проверить, что сайт на Production их не вызывает.
  - Удалять через `RETIREMENTS`.
  - Серверные изменения только добавляют: новые вызовы появляются рядом со старыми.
- **Ничего, что меняет права доступа, правила Firestore, видимые цвета или форматы**,
  не делать без ответа владельца на соответствующий вопрос «К».

### Живая проверка для Ч1.1

Исправление готово, но не выпущено. Документация Google не говорит прямо, какой адрес
сервер первого поколения дописывает в конец `X-Forwarded-For`. Если это адрес Google, а не
посетителя, все посетители попадут в один общий лимит, и анкеты и автосохранение
перестанут проходить у всех компаний сразу. Поэтому сначала — проверка, только чтение:

- **Второе поколение:** подпишите любой документ сами (после 2026-10-11) и откройте
  его последнюю страницу: строка `IP ADDRESS` должна совпасть с вашим адресом, который
  показывает сайт whatismyipaddress.com с того же подключения.
- **Первое поколение:** отправьте сами форму «интересуюсь» по ссылке водителя и в
  Firebase Console → Firestore у появившегося лида (`referral_…`) сравните поле
  `contactConsent.ip` с вашим адресом. Разные адреса у разных лидов ничего не
  доказывают: это могут быть разные адреса Google.

Если оба адреса настоящие, Ч1.1 выпускается одним PR (тесты уже написаны).
