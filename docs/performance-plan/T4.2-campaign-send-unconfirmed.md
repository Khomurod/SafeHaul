# T4.2. Make campaigns safe when the SMS provider does not answer: honest label, no automatic re-text, batches that end before the function limit

[← Plan, progress and owner decisions](README.md) · Checked at commit `11626a6` on 2026-11-03; re-check line numbers against the current `main` before you start.

- **Checklist item(s):** #12 — Set timeouts for external API calls (what a campaign does when a send times out)
- **Size:** M · **Pull requests:** 1 · **Depends on:** T4.1 (`BaseAdapter.SEND_UNCONFIRMED`; T4.3 later makes 8x8 throw the same code, which this task then handles too) · **Owner decision needed:** Q1 — when the SMS provider does not answer a campaign text in time, the text may or may not have reached the driver. Should **Retry Failed** leave those recipients out, so no driver gets the same text twice? *Recommended: yes.* Q2 — should a campaign **pause itself after 3 such texts with no sent text between them** (the provider is clearly not answering; the count carries over from one batch of 50 to the next, and only a sent text resets it, so after Resume one more such text pauses it again), so the recruiter presses Resume once it works, instead of the rest of the list being marked "may have been sent"? The screen shows only "Paused"; the last report rows say why. *Recommended: yes.* If the owner says no to one of them, skip the steps marked [Q1] or [Q2].
- **Why it matters for users:** After T4.1 a campaign text that RingCentral never answered is logged as an ordinary failure: the report says "Not sent", and **Retry Failed** would text that driver again although the first text may have arrived. A batch that runs into the 540-second function limit is also killed in the middle of a send, and Cloud Tasks then texts the recipient being sent again. This task labels such texts honestly, keeps them out of one-click re-sends, and makes every batch stop starting sends in time.

## Current behaviour (verified at 11626a6)

- A send that throws is logged `status: 'failed'`, `isSuccess: false`, `error: err.message` (`functions/bulkActions/workers/sendLoop.js:164-168, 171-179`); no field says the text may have gone out.
- `retryFailedAttempts` takes every log with `status == 'failed'` (`functions/bulkActions/controllers/sessionController.js:218-219`) and starts a new campaign that texts them all again (`:223-269`). Both confirm dialogs tell the recruiter it "messages every failed recipient from this run again" (`src/features/campaigns/components/DetailedReportModal.jsx:199`, `src/features/campaigns/components/CampaignDetails.jsx:387`; code comment `DetailedReportModal.jsx:96-99`). The button shows whenever `progress.failedCount > 0` (`CampaignDetails.jsx:207, 264-266`) or any log failed (`DetailedReportModal.jsx:128`).
- When nothing is left to retry the server returns `{ success: true, message: 'No failed items to retry.' }` (`sessionController.js:221`) and both screens then show "Retry session started with undefined targets." (`CampaignDetails.jsx:124-125`, `DetailedReportModal.jsx:111-112`). For `success: false` both show `result.data.message` as an error toast (`CampaignDetails.jsx:127-129`, `DetailedReportModal.jsx:114-117`).
- The report labels every unsent log "Not sent" in the danger tone with the reason (`src/features/campaigns/constants/campaignConstants.js:54-63`), rendered by `CampaignResultsTable.jsx:38-50` (reason in danger red, note muted; a `warning` icon already exists at `:11`) and `DetailedReportModal.jsx:30-50`. The label "Delivery not confirmed" is already taken by a delivered-but-unconfirmed text (`campaignConstants.js:43`), so the new state needs a different word. The "Not sent" stat card counts `progress.failedCount` (`CampaignDetails.jsx:302-307`).
- A batch has no time budget: up to 50 sends (`functions/bulkActions/workers/batchWorker.js:131`) in a 540 s function (`:43`). With T4.1, a fully hung RingCentral costs about 20.1 s per recipient (20 s limit plus the 0.1 s minimum pause, `sendPacing.js:12-15`), so about 26 recipients fit before the platform kills the batch mid-send. The recipient in flight then has no log, the request ends in an error, and Cloud Tasks retries a failed task by default (the queue is created with default settings, `docs/production-readiness-runbook.md:66-70`; `enqueueWorker` sets no retry or deadline, `functions/bulkActions/services/queueService.js:36-55`; the live queue settings were not read). The next run's idempotency check (`sendLoop.js:77-87`) finds no log for that recipient and texts them again.
- Stopping a batch early is already supported: the pointer advances per processed recipient inside the log transaction (`sendLoop.js:186-218`); after the loop the worker continues from `max(persisted, start + advanced)` and enqueues the next batch while the session is active (`batchWorker.js:234-255`); a paused or cancelled session stops without enqueueing (`:229-232`); Resume sets `active`, bumps the worker generation and re-enqueues (`sessionController.js:143-186`).
- The delivery check only looks at accepted texts (`functions/bulkActions/delivery/deliveryState.js:29-33`), so unconfirmed ones are never "checked" — unchanged here.

## Scope

- In: (a) a `sendUnconfirmed: true` field on the log of a send that threw `BaseAdapter.SEND_UNCONFIRMED`; (b) the report label "May have been sent" (warning) for those logs; (c) a 270-second send window per batch; [Q1] `retryFailedAttempts` leaves `sendUnconfirmed` logs out, says so when nothing is left, and both confirm dialogs say so; [Q2] pause after 3 unconfirmed sends with no sent text between them, counted in the session's `progress` beside the pointer so the count survives the batch boundary, and no next batch after them; tests; APP_BRIEF §8; `docs/firestore-data-model.md`.
- Out (do not do in this task): any change to the adapter (T4.1, T4.3); a stored pause reason or showing one on screen (nothing would read the field, and `retryFailedAttempts` copies every session field into the retry session, `sessionController.js:231-237`); counting unconfirmed texts in `progress.successCount`, the "Not sent" stat card or the 7-day "recently messaged" ledger; the delivery check reconciling unconfirmed texts; fixing the plain "No failed items" toast (open question); any new Firestore query (the retry filter runs in code on the existing single-field query, so no index); backfilling old logs (none have the field; nothing to migrate); new e2e seed rows.

## Risks and safeguards

- Mixed timing: the server part applies to Production at merge, the label and dialog text only after promotion. Until then Production shows "Not sent" plus the new "may have gone out" reason, and its dialog still says "every failed recipient" although Retry Failed now leaves unconfirmed ones out [Q1]. Name this in the PR; it is safe in the direction of sending less.
- [Q1] A driver whose text really did not arrive is not re-texted by Retry Failed; the note tells the recruiter to text them directly. This is the owner's trade-off.
- [Q2] A campaign paused by the worker shows only "Paused"; the last report rows explain why. The status-checked transaction keeps a cancel from being undone.
- [Q2] If the pause write fails, the session stays active with no next batch (logged as an error); Pause then Resume, or Cancel, recover it. This errs toward sending less.
- Unconfirmed texts still count in `progress.failedCount` and the "Not sent" card; listed as a known limit in the PR.
- The window can only make a batch shorter; the next batch continues from the stored pointer, which is already how pause, resume and mid-batch cancels work; `i > 0` keeps every batch moving.
- Rollback: revert the PR. The added log field and `progress.unconfirmedInARow` are optional, and nothing outside this task depends on them.
