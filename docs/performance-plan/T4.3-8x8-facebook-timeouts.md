# T4.3. Add time limits to the 8x8 SMS and Facebook Graph calls

[← Plan, progress and owner decisions](README.md) · Checked at commit `11626a6` on 2026-11-03; re-check line numbers against the current `main` before you start.

- **Checklist item(s):** #12 — Set timeouts for external API calls (8x8, the alternate SMS provider, and Facebook Graph)
- **Size:** S · **Pull requests:** 1 · **Depends on:** T4.1 (reuses `BaseAdapter.sendUnconfirmedError`) · **Owner decision needed:** none
- **Why it matters for users:** A company on 8x8 has the same exposure as RingCentral had: a send that never gets an answer waits until the function is killed. Connecting a Facebook page (an admin action) can also spin for a minute. After this task 8x8 calls give up after 20 seconds and Graph calls after 15, with the same "may have gone out, not resent" rule for an unanswered 8x8 text.

## Current behaviour (verified at 11626a6)

- Only two files use axios in `functions/`: `functions/integrations/facebook.js:7` and `functions/integrations/adapters/eightbyeight.js:2`; there is no `axios.create` or `axios.defaults` anywhere. axios 1.20.0 (`functions/package-lock.json:3284-3287`) sets no time limit by default. Context7 `/axios/axios` (error-handling docs): the per-request `timeout` option rejects with `code: 'ECONNABORTED'`, or `'ETIMEDOUT'` with `transitional.clarifyTimeoutError: true`; `ECONNABORTED` is also used for an aborted request.
- 8x8 send: `axios.post` with only headers (`eightbyeight.js:70-83`); the catch wraps every error as `8x8 Error: …` (`:97-100`), so a timeout would look like a plain failure. The 8x8 adapter has no `sendSMSWithReceipt`, so campaigns call its `sendSMS` (`functions/bulkActions/workers/sendLoop.js:133-137`).
- 8x8 verify: `axios.get` probe (`:134-142`); the catch treats every error other than 401/403 as "auth worked" (`:143-151`). Once a limit exists, a timeout would be reported as a **successful** connection unless it is handled.
- Facebook: `connectFacebookPage` (callable, default 60 s; `facebook.js:41-43`) makes three Graph calls in a row: token exchange `:181-188`, page token `:197-202`, subscribe `:225-230`. Any failure releases the claim and throws `HttpsError('internal', 'Failed to connect Facebook Page.')` (`:233-247`). The webhook's lead fetch (`:378-382`) throws to the handler, which answers 500 (`:345-347`), so Meta delivers the event again. Lead capture is switched off (`docs/APP_BRIEF.md:1307-1309`), but both functions are still deployed (`functions/index.js:172-173`).
- 8x8 callers are the same as RingCentral's, through the factory (`functions/integrations/factory.js:154-160`), plus the direct verify calls (`providerConfigController.js:258-260`, `environmentVault/index.js:338-340`, `lineConnectionController.js:163`).
- No existing test builds the real 8x8 adapter (every suite that names it mocks it as an empty class).

### Values

- 8x8: 20 s — the same reasoning as T4.1 (a signer or contact SMS trigger has 60 s and must still record the result).
- Graph: 15 s — three calls in a row in a 60 s callable is 45 s at worst, which leaves time to release the claim and stays inside the browser's 70 s callable limit; Graph normally answers in well under a second.

## Scope

- In: `timeout` on all six axios calls; a timed-out 8x8 send becomes `BaseAdapter.sendUnconfirmedError('8x8', 20)`; a timed-out 8x8 verify is a failure; tests; APP_BRIEF §7.
- Out (do not do in this task): the browser's Facebook page list (`src/features/settings/components/IntegrationsTab.jsx:111`, lead capture is off); 8x8 verify's treatment of other network errors as success (pre-existing, open question); any change to the Facebook claim logic; a global `axios.defaults` (a per-call setting is clearer and cannot leak to another caller); no index, CSP or data change.
