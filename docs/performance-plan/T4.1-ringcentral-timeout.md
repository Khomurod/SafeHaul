# T4.1. Give every RingCentral request a 20-second limit and never resend a text RingCentral did not answer

[← Plan, progress and owner decisions](README.md) · Checked at commit `11626a6` on 2026-11-03; re-check line numbers against the current `main` before you start.

- **Checklist item(s):** #12 — Set timeouts for external API calls (RingCentral, the primary SMS provider)
- **Size:** M · **Pull requests:** 1 · **Depends on:** none · **Owner decision needed:** none
- **Why it matters for users:** Today, if RingCentral stops answering, a campaign batch, a signer's SMS or an automated contact SMS waits until the Cloud Function is killed (up to 9 minutes for a campaign batch), and nothing records what happened to the text. ### Why 20 seconds

- Every signer or contact SMS builds a new adapter (`functions/integrations/factory.js:154-160`), so it makes two RingCentral calls in a row (log-in, then the send): 2 × 20 s = 40 s, inside the 60 s trigger limit, leaving time to record `smsStatus: 'failed'`. With 30 s the two calls could use the whole 60 s and the function would be killed before it records anything.
- RingCentral normally answers a send in about a second, so 20 s leaves wide room for a slow but working service.
- In a campaign, a hung send costs one recipient 20 s instead of the rest of the 540 s batch. In `checkCampaignDelivery` (120 s) a hung page ends at 20 s with the existing "could not be reached" message.
- One value for every RingCentral request keeps it simple; node-fetch applies it separately to waiting for the answer and to reading it.

### Behaviour on timeout (defined by this task)

- The send request itself times out → error with `code: 'sms-send-unconfirmed'` and message `RingCentral did not answer within 20 seconds, so SafeHaul cannot tell whether this text went out. It was not sent again.` It is never retried: no rate-limit retry, no from-line fallback, no default-line fallback. This is deliberately conservative: a token refresh that the SDK runs inside the same `post` and that times out also counts as unconfirmed.
- A timeout before any send (the log-in at `ringcentral.js:85`, or the re-log-in after a rate-limit wait at `:220`, which only follows a 429 that sent nothing) → `RingCentral Error [Timeout]: RingCentral did not answer within 20 seconds. Nothing was sent; try again later.`
- RingCentral accepted the send but its answer stalls while being read → unchanged: `ringcentral.js:207` turns it into a success without a receipt; the delivery check later matches it by number and time.
- Reads (`listSentSms`, inventory, verify, test line, add-line check) → the `FetchError` reaches the existing error paths.

## Risks and safeguards

- Cloud Functions are shared: merging changes SMS behaviour for Production users at once, with no promotion step. The change only adds a limit and clearer errors; rollback = revert the PR (the revert's merge redeploys the functions).
- A slow but working RingCentral (over 20 s) would now fail sends that used to succeed late. They are reported as "may have gone out" and not resent, so no driver gets a duplicate; the logs show how often it happens.
- An SDK upgrade that moves to built-in fetch would silently ignore `timeout`: test (1) reads the limit back from a real request and fails if that happens.
- Conservative labelling (a refresh timeout counted as unconfirmed) can only ever stop a resend, never cause one.
- Pre-existing and unchanged: `resendSignerOnCorrection` sends the email first, so a slow SMTP server plus a silent RingCentral can still reach its 60 s limit before `smsStatus` is recorded. The trigger does not retry, so this cannot double-send; it is listed in the PR, not fixed here.
