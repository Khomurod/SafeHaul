# The SafeHaul component catalog

This is the catalog for SafeHaul's **design system** — the business-neutral
visual contract that owns how reusable interface elements look and behave.

It documents primitives and business-neutral page patterns. It deliberately does
**not** document feature screens, and it does not know that SafeHaul has drivers,
recruiters, carriers or signing requests. Fixtures here talk about *records*,
*owners* and *references*; features supply the real domain words at the call
site.

## Before you change UI code

Read these, in order:

1. `docs/SAFEHAUL_DESIGN_SYSTEM_ROADMAP.md`
2. `src/design-system/README.md`
3. The component or pattern documentation in this catalog

## Approval status

Every page in this catalog states a status. **Not everything here is approved**,
and the difference matters — an honest catalog is more useful than a flattering
one.

| Status | Meaning |
| --- | --- |
| **Approved** | The component is proven by real consumers, has behaviour and accessibility tests, and should be reused as-is. |
| **Needs review** | Built from approved primitives, but something about it is unsettled — a missing primitive, an open roadmap item, or verification that has not been automated yet. Usable, but read the caveat before copying it. |
| **Temporary** | A compatibility shim that exists only until a migration finishes. Do not add new consumers. |

Where a page says *Needs review*, it says exactly what is unresolved. Those
caveats are the roadmap's open items, not hedging.

**The visible families are owner-approved.** The owner approved the semantic
brand and action colours as they stand and confirmed WCAG 2.2 AA as the
permanent standard; the roadmap records both as standing rulings (sections 1 and
6). A page marked *Needs review* is waiting on something specific to itself, not
on a palette or a standard.

## Icons

Every glyph comes from `@design-system/icons`, and it arrives as a **token**
rather than a component:

```jsx
import { Icon, Trash2 } from '@/design-system/icons';

<Icon icon={Trash2} size="sm" />        // decoration — announced by nothing
<Icon icon={Trash2} label="Delete" />   // the glyph IS the control
```

Sizes are the seven steps `xs sm md lg xl 2xl 3xl` (12–32px), never a pixel
number — `<Trash2 size={13} />` throws by name. A container that already sizes
the glyph inside it (`Button`, `IconButton`, `Tabs`, `SegmentedControl`,
`FileInput`, `Chip`, `StatusMedallion`) still wins, so an icon in a small button
is small because the button says so.

**Every file in the application is on this contract**, and the rule has no
exception list to add to. Where a container's real geometry cannot be expressed on
the scale (a 12px drag handle, a 128px logo frame), the container carries the size
and the arithmetic is recorded at the call site. See **Foundations → Icons**.

## Known gaps

**The authoritative list lives in one place, and it is not here.**
`docs/SAFEHAUL_DESIGN_SYSTEM_ROADMAP.md` section 5 — "Missing primitives that
live code is waiting on" — records every gap with the call sites that cite it and
the reason the nearest primitive does not fit. This page used to repeat that
list, and so did `src/design-system/README.md`; three copies of a list that
changes every slice is three chances to read a stale one.

What still belongs here is the rule, not the inventory: **do not hand-roll a
primitive that does not exist yet.** Record the need in section 5, with the call
site and what the nearest existing primitive cannot express. A hand-rolled one
becomes a second implementation the moment the real one lands, and this catalog
records that mistake happening twice already.

The same goes for a shape the design system already owns. A **hand-composed
pattern** — a card with a medallion, heading, body and actions, or a dialog with
its own cancel-and-confirm footer — is made entirely of approved primitives, so
it passes every automated rule while duplicating a pattern that exists. Use
`patterns/page-state` and `ConfirmDialog`.

## Rules the families carry

Each family's own page holds its full contract; these are the rules that cut
across them, or that are easiest to get wrong.

- **Use the primitive, never a hand-rolled copy.** Tab strips use `TabList` /
  `TabPanel`, toggle groups `SegmentedControl`, file pickers `FileInput`, and
  status screens, panel-level empties and confirmation dialogs
  `patterns/page-state` or `ConfirmDialog`. Every approved native `<table>`
  applies the `ds-native-table` contract, so a table that is not `DataTable`
  still gets `DataTable`'s header, divider, density and cell padding from the
  same `--ds-table-*` roles.
- **Hand-rolled shapes are refused**: a raw `<button>` carrying `aria-pressed` or
  `aria-current`, a round disc holding a person's initial, and a
  `<button aria-expanded>` **inside a heading**. That last scope is the whole
  rule: menus, a combobox, a navigation group, a drawer and a filter toggle use
  `aria-expanded` too, and `Disclosure` replaces none of them. `SegmentedControl`
  and `Chip` are the toggle shapes, a `Button` with `pressed` is the third, and
  `SelectableCard` is the card. A step indicator that is read rather than
  operated has no primitive yet and is recorded as an open gap rather than
  demanded by a rule.
- **`Link` / `ButtonLink` / `IconButtonLink`**: `external` opens a new tab and
  announces it. Do not hand-write `target="_blank"`.
- **`Button variant="link"`** is an action that reads as inline text. It is
  still a `<button>`, because it acts rather than navigates; use `Link` when the
  address bar changes.
- **`pressed` on `Button` and `IconButton`** is for a toggle that must keep its
  variant. It draws a fill and an inset ring at a specificity nothing
  feature-side can beat — which is the point: a text utility marking the active
  state loses silently to the variant's own `color` rule.
- **`Chip` / `ChipGroup`** is the interactive twin of `Badge`: the same pill, the
  same 12px semibold text, the same six tints, plus a pointer, a focus ring and a
  pressed state. It is both the filter chip and the tinted chip link.
- **`SelectableCard`** is a block of record content that behaves as one option —
  an FMCSA suggestion row, a lead row, a company row, a page thumbnail.
  `selected` and `current` are two different ARIA answers that render
  identically on purpose, and passing both throws.
- **`Avatar`** is the disc standing for a person or an organisation. Its scale is
  not ours: all five steps are GitHub Primer's, which is also where the
  responsive `{ base, sm }` size and the
  circle-for-a-person/square-for-an-organisation rule come from. It is always
  `aria-hidden` with no way to opt out: a bare initial beside the name it
  abbreviates is noise.
- **`Input variant="inline"`** is a field inside running content rather than a
  form. It is deliberately *not* the published `InlineEdit` pattern — none of its
  consumers has a read view — and it refuses to render without a name, because it
  has no `FormField` wrapper to give it one.
- **`Disclosure`** is a collapsible section whose trigger sits inside a heading.
  `variant="card"` is a prominent titled section — leading slot, `heading-sm`
  title, a description line, a 24px chevron — that does *not* draw the card it is
  named for: `Card` owns the surface, and the variant only takes off the rail
  chrome that would fight it. `description` and `leading` throw on the rail;
  `meta` throws on a card.
- **`SectionNavigation` as a step rail**: `currentType="step"` (what ARIA
  defines for a position in a process), a per-item `status` announced as part of
  the item's name rather than shown by colour, an optional `group.label`, and
  `frame="none"` for a rail inside a container that already draws one.
- **`Notice`**, the tinted message block. Every default in it is a number from
  its audit rather than a preference — see its page. Its **actions sit under the
  message**, the order Atlassian's `SectionMessage` and Polaris' `Banner` both
  use, and `titleAs` is for a title that is a real heading. A tinted block that
  holds form controls is a region, not a notice.
- **The brand colours** (`ds-brand-primary`, `ds-brand-accent`): the accent is
  for the inverse surface only — on a light one it is about 1.6:1.
- **`PageState`** takes `titleId`, `children` and `focusOnMount`; its story page
  documents all three.

Every remaining exception in the product carries a written reason; none is
marked as migration debt. That does not make the gaps above less real — an
exception with a good reason is still a call site waiting for a primitive.

## Appearance

SafeHaul ships a **light appearance only**. There is no `prefers-color-scheme`
rule, no `data-theme` attribute and no dark token set anywhere in the product, so
this catalog does not offer a dark-mode toggle — a switch that rendered something
the application cannot produce would be worse than none.

The backgrounds toolbar does offer an **inverse surface**. That is a *role* for a
specific kind of content — console and log output panels — not an appearance
setting.

## Viewports

Three presets, matching the widths SafeHaul reviews at:

- **Desktop — 1440**
- **Tablet — 1024**, where table action columns first compete for space
- **Mobile — 412**

Pattern stories carry explicit stories at all three.

## Safety guarantees

The catalog is safe to build and host anywhere:

- **No Firebase, Cloud Functions, Storage or any network call.** Nothing here
  imports application context or domain services, and
  `src/design-system/tests/architecture.test.js` fails the build if design-system
  code ever does.
- **No secrets.** The CI job that builds this catalog is given no credentials.
- **No production data.** Every value comes from
  `src/design-system/stories/fixtures.js`, which is entirely hand-written
  literals — no `Math.random`, no `Date.now()`, no generated data. Stories render
  identically on every run.
